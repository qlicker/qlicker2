# Development Guide

This guide explains how to work on the current Fastify + React Qlicker codebase.

## Local development

Use Node.js 22.13 or newer. MongoDB is required; Redis is recommended when exercising realtime fan-out. Keep secrets in the untracked root `.env` generated by setup.

### Install dependencies

```bash
npm ci --prefix server
npm ci --prefix client
```

### Dependency maintenance

The client, server, and load-test seeder have separate manifests and lockfiles. Update both files in each affected workspace and keep the seeder's Mongoose and Argon2 versions aligned with the server. Use `npm outdated --prefix <workspace>` to inspect available updates and `npm audit --prefix <workspace>` to check advisories. Review major upgrades separately; do not use `npm audit fix --force` to apply unreviewed migrations or downgrades.

Some dependencies have explicit security overrides. The client uses its direct KaTeX version for the Markdown math pipeline as well as the question editor, so older nested copies cannot remain installed. The server pins patched `@xmldom/xmldom` on the 0.8 maintenance line for SAML and patched static-file/glob dependencies. Review these constraints when updating their parent packages, and verify the resolved tree with `npm ls --prefix <workspace> --all`.

Dependency validation includes the client and server suites, client production build, load-test infrastructure tests, and browser workflows. The email integration test uses the real Nodemailer SMTP transport against an isolated loopback fixture; the Markdown math tests exercise the real rendering pipeline and its trust restrictions. After upgrading Playwright, install its matching browser with `cd client && npx playwright install chromium` before running E2E tests. On a resource-constrained machine, pass `-- --maxWorkers=4` to each workspace's `npm test` command.

Rebuild Docker images to deploy dependency updates; pulling the source alone does not change packages inside an existing image. Smoke-test your configured SMTP delivery and SAML identity provider after deploying mail or SAML dependency updates.

### Run the app

Use the repository scripts when possible:

```bash
./scripts/setup-native.sh
./scripts/qlicker.sh start
```

On Linux, this also starts the system monitor with the root `.env` Mongo/Redis and monitoring settings. Use `./scripts/qlicker.sh status`, `stop`, or `restart` to manage the complete native stack. The collector writes `.data/system-monitor.log`; `SYSTEM_MONITOR_LOG_PATH` overrides that location. Its PID is tracked both in `.qlicker.pids` and `.data/system-monitor.pid` so stopping still finds the collector if the main PID file is lost. A collector failure leaves the app available and appears as stopped in status; restart the stack after correcting the problem. Set `SYSTEM_MONITOR_ENABLED=false` to opt out.

The collector runs with a 64 MiB V8 old-space limit and lower CPU scheduling priority (`nice 10` when available). These are not Docker's hard total-memory/CPU limits; use a native supervisor/cgroup for equivalent hard limits. Native controller lifecycle regressions use isolated fixture processes and ports:

```bash
node --test scripts/test/qlicker-native.test.mjs
```

Or run the two app halves manually:

```bash
npm run dev --prefix server
npm run dev --prefix client
```

Run those manual commands in separate terminals. The root development Compose file is not the production deployment; use `production_setup/` for production.

### Default local addresses

Setup can change these ports; use the generated `.env` when checking a particular installation.

| Service | Default address |
| --- | --- |
| Web app | `http://localhost:3000` |
| API | `http://localhost:3001/api/v1` |
| API health | `http://localhost:3001/api/v1/health` |
| Admin-protected API docs | `http://localhost:3001/docs` with `ENABLE_API_DOCS=true` |

For Docker development, use `./scripts/setup-docker.sh` followed by `docker compose up -d --build` from the root. See the [README](../../README.md#try-it-with-docker) for host requirements and the first-run account workflow.

## Testing and verification

Verified commands for the current repository:

```bash
npm test --prefix server
npm test --prefix client
npm run build --prefix client
```

Playwright E2E coverage is available with:

```bash
./scripts/qlicker.sh e2e
# or
cd client && npm run test:e2e
```

The Playwright suite starts isolated app services and an in-memory MongoDB. If a local `.env` points at Redis that is not running, use the service wrapper or clear `REDIS_URL` for the isolated run.

## How to approach a change

1. Read `AGENTS.md` and `CODING_STANDARDS.md`.
2. Read `meteorjs_migration/LEGACY_DB.md` if persisted data or old installations are affected.
3. Find the user role and route area the change belongs to.
4. Identify the route schema, permission, service, model, client, and realtime impact.
5. Add or update tests near the changed behavior.
6. Update user/developer/operations documentation in the same change.
7. Run targeted validation and then broader validation appropriate to the risk.

## Common implementation locations

### Add or change a frontend page

Look in:

- `client/src/pages/...`
- `client/src/components/...`
- `client/src/contexts/...`
- `client/src/i18n/locales/*.json`

### Add or change an API route

Look in:

- `server/src/routes/...`
- `server/src/services/...`
- `server/src/models/...`
- `server/test/routes/...`
- `docs/api-reference.md`

Route schemas feed Swagger/OpenAPI. With `ENABLE_API_DOCS=true`, verify the result at `/docs` and `/docs/json`.

### Add or change real-time behavior

Look in:

- `server/src/routes/sessions.js`
- `server/src/routes/websocket.js` or websocket helpers in the app
- client pages or contexts that subscribe to live updates

Keep frequent paths delta-driven and preserve a targeted fallback refresh for incomplete or legacy events. Use the load-testing suite for changes that can amplify work per connected student.

### Add or change grading behavior

Look in:

- `server/src/services/grading.js`
- `server/src/routes/grades.js`
- `server/src/routes/sessions.js`
- `client/src/components/grades/...`
- `docs/developer/grading.md`

## Documentation expectations

When you change visible behavior, update the related docs:

- user-facing workflow changes -> `docs/user-manual/`
- developer-facing architecture/data/API changes -> `docs/developer/` and `docs/api-reference.md`
- deployment or ops changes -> `production_setup/README.md`

The in-app user manual is localized under `client/src/i18n/locales/`. Detailed Markdown manuals and browser illustrations live under `docs/user-manual/` and `docs/assets/manuals/`.

Regenerate browser illustrations with synthetic E2E data:

```bash
cd client
REDIS_URL= QCLICKER_CAPTURE_MANUALS=1 npx playwright test e2e/manual-screenshots.spec.js e2e/admin-system-monitoring.spec.js --project=chromium
```

The capture is skipped without the opt-in variable and writes identical images to the Markdown and in-app asset directories. The landing-page and anonymous-review illustrations have a separate focused command:

```bash
cd client
REDIS_URL= QCLICKER_CAPTURE_MANUALS=1 npx playwright test e2e/public-overview.spec.js --project=chromium
```

The anonymous review test also runs as a normal browser regression without the capture variable; only screenshot writing and the landing-page capture require opt-in.

## Security and operational expectations

The current app includes:

- JWT access tokens plus refresh-cookie workflows
- CSRF/CORS enforcement
- auth lockout after repeated failures
- file-upload validation
- WebSocket and upload rate limiting
- optional Redis fan-out for multi-instance WebSocket delivery
- SAML login/logout support

When you touch auth, uploads, settings, or WebSockets, re-check the relevant protections rather than assuming they stay correct automatically.

Two current implementation details are easy to miss:

- runtime storage selection is database-driven (`Settings.storageType`) and defaults to local until an admin changes it in the UI
- auth-related settings such as SSO enablement, SAML advanced options, token/session lifetime, upload width, and avatar thumbnail size should take effect immediately after save, so avoid adding caches that delay those changes
- global AI backend policy is separate from per-course enablement and student model availability; never return backend tokens in client-visible payloads
